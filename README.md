# CRM for Me

Личный Telegram CRM-бот для одного владельца: пересылка сообщения клиента →
дозаказ → выполнение → счёт по требованию → частичная или полная оплата.

## Что реализовано

- Клиенты и проекты, произвольные поля, заметки, архивирование с сохранением истории.
- Быстрый дозаказ из пересылки. Известный Telegram ID определяет клиента;
  скрытый отправитель требует выбора или создания карточки. Создать проект можно
  прямо в этом диалоге, исходное сообщение при этом сохраняется.
- Пересылка от известного Telegram ID сразу сохраняет новую задачу с ценой 0 ₽;
  цену можно изменить в карточке. Единственный неархивный проект выбирается
  автоматически; при нескольких проектах задача уже сохранена, остаётся выбрать проект.
- Сообщения того же клиента с паузами меньше 5 секунд между пересылками в бот
  дополняют одну задачу. Пауза от 5 секунд создаёт новую. Все тексты и ключи
  сообщений сохраняются в БД: повторная пересылка не дублирует ни задачу, ни текст.
  Завершённые и отменённые задачи не дополняются. Скрытого отправителя по имени
  бот не угадывает — для него сохраняется ручной выбор клиента.
- В главном меню — новые задачи и задачи в работе, по 5 на страницу, с переходом
  в карточку. Если их нет — финансы за всё время по сохранённым счетам: начислено
  (включая черновики), выставлено, оплачено, долг. Отменённые и заменённые счета
  исключены. Из карточки задачи доступно «🏠 Главное меню».
- Ручные задачи, изменение названия/описания/цены, статусы NEW, IN_PROGRESS,
  DONE, CANCELLED. Исходный текст пересылки хранится отдельно.
- В списке задач клиента или проекта есть «➕ Добавить задачу». Можно сразу
  написать название сообщением: бот спросит сумму и сохранит задачу в открытом
  контексте. Для бесплатной задачи введите 0; /cancel отменяет создание.
- Регулярные месячные услуги: создание, изменение цены, отключение.
- «Серверы» в главном меню и «Сервер» у клиента: IP (IPv4/IPv6), ежемесячный
  платёж, изменение IP/цены, отключение. Начисление с текущего месяца, один раз
  в месяц; старые выставленные счета сохраняют прежний IP и тариф.
- Счета по требованию: несколько счетов в месяц, отдельная история по номерам,
  позиции и оплаты каждого счёта; дашборд и детализация по клиентам.
- Выбор отдельных позиций из разных неоплаченных счетов одного клиента и объединение
  в общий счёт с сохранением исходной истории.
- Частичные оплаты, защита от переплаты и повторной записи одного платежа.
  «Принять оплату» доступно и в черновике: после проверки суммы бот одновременно
  выставляет счёт и записывает платёж. Долг в сводке включает черновики.
- «Корректировать счёт» → позиция → название/сумма → подтверждение. Доступно
  и после частичной оплаты; итог не может быть ниже полученной суммы. Исходные
  позиции и оплаты сохраняются, все корректировки видны в истории позиции.
  Корректировка черновика остаётся в силе при изменениях исходной задачи/услуги.
- Поиск по клиентам, Telegram username, компании, проектам, задачам и значениям полей.
  Результат открывает карточку, включая архивные записи.
- Напоминания только владельцу. Сохранённые напоминания переживают перезапуск.
- Пагинация списков, `/start`, `/cancel`, сообщения об ошибках без traceback.

Стек: Python 3.12+, aiogram 3, SQLAlchemy 2 / asyncpg, PostgreSQL 16, Alembic.
Один процесс бота и одна БД; Redis, Mini App и веб-сервер не нужны.

## Запуск в Docker

```bash
cp .env.example .env
# Заполните .env перед следующей командой.
docker compose up -d --build
docker compose logs -f bot
```

В `.env` обязательны:

- `BOT_TOKEN` — токен вашего бота из BotFather.
- `OWNER_TELEGRAM_ID` — ваш числовой Telegram ID, больше нуля.
- `POSTGRES_PASSWORD` — уникальный пароль БД; для Compose используйте
  буквы, цифры, `-` и `_`, чтобы он был пригоден для URL.
- `DATABASE_URL` — для локальных команд укажите тот же пароль и `localhost`.
  В контейнере Compose автоматически использует хост `db`.

`TIMEZONE` задаёт часовой пояс интерфейса и расчётного месяца. Учёт MVP — только RUB.
`REMINDER_INTERVAL_SECONDS` — интервал проверки напоминаний, по умолчанию 30 секунд.
`ALEMBIC_DATABASE_URL` необязателен: миграции по умолчанию используют `DATABASE_URL`.

Контейнер ждёт готовности PostgreSQL, применяет миграции и запускает polling.
База доступна на localhost; сменить порт можно через `POSTGRES_PORT`.
Данные находятся в Docker volume `pgdata`. **Не используйте `docker compose down -v`
для обычной остановки.** Запускайте один polling-процесс на токен.

После запуска откройте личный чат с ботом и отправьте `/start`. Обновления от других
пользователей и из групп отбрасываются до обработчиков.

## Локальная разработка

```bash
python3.12 -m venv .venv
. .venv/bin/activate
pip install -r requirements.lock
pip install -e '.[dev]'
cp .env.example .env
# Заполните .env.
docker compose up -d db
alembic upgrade head
crm-bot
# Равнозначно: python -m app.main
```

## Проверки

Быстрые тесты SQLite проверяют логику, но не заменяют PostgreSQL:

```bash
ruff check app tests alembic
ruff format --check app tests alembic
pytest -q
```

Полный прогон на отдельной PostgreSQL (никаких рабочих данных):

```bash
docker run -d --name crm-test \
  -e POSTGRES_USER=crm_test -e POSTGRES_PASSWORD=crm_test -e POSTGRES_DB=crm_test \
  -p 127.0.0.1:55439:5432 postgres:16-alpine
export TEST_DATABASE_URL=postgresql+asyncpg://crm_test:crm_test@127.0.0.1:55439/crm_test
DATABASE_URL="$TEST_DATABASE_URL" alembic upgrade head
DATABASE_URL="$TEST_DATABASE_URL" alembic check
pytest -q --cov=app --cov-report=term-missing
```

Дождитесь готовности контейнера (`docker exec crm-test pg_isready -U crm_test`).
Если задан `ALEMBIC_DATABASE_URL`, уберите его или также направьте на тестовую БД.
Имя тестовой базы должно начинаться с `crm_test`: тесты очищают её таблицы перед каждым
сценарием. Они используют схему, установленную миграциями, а не `create_all`.
Старые тесты моделирования конфликта в `test_billing_integrity.py` используют SQLite;
действительные параллельные подключения проверяются в `test_postgres_concurrency.py`.

CI выполняет lint, проверку форматирования, миграции, проверку соответствия ORM,
тесты на PostgreSQL и сборку Docker. Сквозные тесты отправляют Telegram Update
в настоящий диспетчер, подменяя только транспорт Telegram API.

## Правила учёта

- Суммы — Decimal / NUMERIC, без float. Отрицательные и неконечные значения запрещены.
- Задача начисляется в месяц выполнения по `TIMEZONE`. Повторное «Выполнено» безопасно.
- Регулярная услуга начисляется **полностью за каждый месяц пересечения периода действия**,
  без пропорционального расчёта по дням. Начисления создаются при запуске бота,
  смене месяца и просмотре дашборда/счёта. Повторная генерация не создаёт дубли.
- До выставления позиции черновика обновляются. После выставления цены и позиции
  фиксируются; изменения источника не меняют исторический счёт.
- Счёт выставляется по кнопке в любой момент. После выставления предыдущего
  новые выполненные задачи попадают в следующий черновик. Оплата старого счёта
  не мешает выставить новый. Месяц остаётся только группировкой начислений;
  черновики прошлых месяцев также можно выставить через историю счетов.
- Путь: «Клиент → Счета → Выставить счёт → Подтвердить». Старые счета доступны
  через «История счетов», каждый открывается и оплачивается по своему номеру.
- Объединение: «Счёт → Позиции → Объединить позиции → выбрать галочками →
  Продолжить → Подтвердить». Можно выбирать позиции на разных страницах.
  Доступны черновики и выставленные счета одного клиента без единой оплаты.
  Новый общий счёт получает статус и расчётный месяц выбранного счёта назначения.
  Остатки сохраняются в отдельных счетах с прежним статусом и месяцем.
- При объединении исходные счета получают статус «Заменён при объединении»:
  их позиции и цены сохраняются, в долг и итоги они больше не входят.
  Кнопка «Новые счета» открывает общий счёт и остаток. Все затронутые позиции
  фиксируются по цене на момент подтверждения, включая позиции черновиков.
  Регулярные услуги сохраняют месяцы исходных начислений для защиты от дублей.
  В месячной сводке перенесённые суммы учитываются в месяце общего счёта;
  история исходных месяцев остаётся в старых счетах.
- Пустой счёт и счёт с итогом 0 ₽ выставить нельзя. Задача должна быть отмечена
  «Выполнено», чтобы попасть в черновик. При нулевом долге оплата не предлагается,
  в том числе для старых пустых счетов. Ввод нулевой оплаты объясняет, что сумма
  должна быть больше 0 ₽.
- Регулярная услуга учитывается один раз за расчётный месяц, даже если за этот
  месяц выставлено несколько счетов. Изменение её цены не создаёт повторного начисления.
- Отключение услуги убирает её из всех черновиков; выставленные счета сохраняются.
- Долг на карточке клиента/дашборде — остаток по выставленным счетам. В черновике
  показывается будущая сумма к оплате. Переплата не поддерживается.
- Платежи и выставленные счета не удаляются через интерфейс. Архивирование обратимо.
- Повторное исходное сообщение распознаётся по доступным данным Telegram.
  Для скрытого отправителя надёжно распознаётся только повторная доставка того же
  update: имя не используется как идентификатор клиента.
- Незавершённый диалог ввода после перезапуска начинается заново; сохранённые
  клиенты, проекты, задачи, счета и оплаты остаются в PostgreSQL.
- Напоминания имеют доставку «как минимум один раз»: сбой между отправкой Telegram
  и фиксацией в БД может вызвать повтор с тем же номером напоминания.

В CRM храните только ссылки на секреты в менеджере паролей, например
`Bitwarden → Project / Production`, а не сами пароли, ключи или токены.

## Автодеплой на рабочем сервере

Проект размещён в `/opt/crm-for-me`. Systemd-таймер `crm-for-me-deploy.timer`
раз в минуту проверяет `origin/main` и успешный push-запуск CI для того же коммита.
После проверки собирается образ с тегом SHA, сохраняется резервная копия БД,
применяются миграции и обновляется только контейнер бота. Том PostgreSQL сохраняется.
Успех фиксируется после запуска Telegram polling именно в новом образе.

```bash
systemctl status crm-for-me-deploy.timer
journalctl -u crm-for-me-deploy.service -n 50 --no-pager
cat /var/lib/crm-for-me-deploy/state.json
```

Рабочая копия должна оставаться чистой на `main`; ручные изменения блокируют деплой.
После сбоя прежний образ возвращается автоматически, если схема БД не изменилась.
Если миграция уже изменила схему, автоматическое восстановление старой БД запрещено;
сохраняются данные, backup и диагностика для восстановления. Неудачный коммит
повторно не запускается до нового коммита или явного `--retry`.
Подробности установки и восстановления — [deploy/README.md](deploy/README.md).

## Обслуживание

Перед обновлением сделайте резервную копию:

```bash
mkdir -p backups
docker compose exec -T db pg_dump -U crm -d crm -Fc > backups/crm.dump
```

Храните копию вне сервера, с ограниченным доступом. Обновление:
`docker compose up -d --build`; контейнер применит новые миграции автоматически.
Если миграция отклоняет старые некорректные финансовые данные, остановитесь,
проверьте копию и исправьте данные осознанно — миграции не удаляют их молча.

Восстановление сначала проверяйте в отдельной БД:

```bash
docker compose exec -T db createdb -U crm crm_restore
docker compose exec -T db pg_restore -U crm -d crm_restore < backups/crm.dump
```

Для отката приложения используйте предыдущий образ. Откат новых миграций удаляет
добавленные колонки/ограничения: на рабочей базе предпочтительно восстановление из
копии, а не безусловный `alembic downgrade`.

Проверяемый пользовательский сценарий и границы проверки: [docs/acceptance.md](docs/acceptance.md).
