# Счета по требованию

## Причина и изменение

Уникальность клиента/месяца разрешала только один счёт. После выставления
завершить новую работу в том же месяце было нельзя. Пустой счёт можно было
выставить, затем бот предлагал оплату при нулевом долге и выдавал общую ошибку на 0.

Теперь в одном месяце можно выставлять несколько счетов, сохраняя один открытый
черновик. Новые выполненные задачи входят в следующий черновик. Регулярная услуга
начисляется один раз в месяц, независимо от числа счетов. Месяц нужен для учёта,
ждать его окончания не требуется. Неоплаченные счета не мешают выставлять новые.

Счета имеют отдельные номера и историю, оплаты привязаны к выбранному счёту.
При нулевом долге кнопка оплаты скрыта; сервер проверяет также старые кнопки.
Пустой или нулевой счёт выставить нельзя. Нулевой платёж объясняет ошибку суммы.
Ранее выставленные пустые счета сохраняются как часть истории.

## Проверено

- PostgreSQL 16: 78 тестов, покрытие приложения 85,13%.
- Сквозные проверки через aiogram Dispatcher/FSM и БД с подменой транспорта Telegram:
  два счёта в одном месяце, история, выбор и оплата нужного счёта, старая кнопка
  оплаты пустого счёта, ввод 0 и последующая корректная оплата.
- Конкурентное завершение двух задач после выставления создаёт один новый черновик.
  Одновременные выставление и завершение задачи сохраняют всю выручку без дублей.
- Миграция копии рабочей БД: upgrade → downgrade → upgrade; контрольные суммы
  всех прикладных строк совпадают. `alembic check` не находит расхождений модели и БД.
- Проверки нового поведения сначала воспроизвели отказ на старой реализации.

## Обновление и восстановление

`0004_on_demand_invoices` меняет только уникальное ограничение на частичный
уникальный индекс для DRAFT; данные и старые миграции не переписываются.
Перед обновлением остановить bot, сохранить `pg_dump -Fc`, применить миграцию
и запустить новый образ. Остановка исключает запись старым кодом в новую схему.

После появления нескольких счетов за месяц автоматический downgrade запрещён:
старое ограничение несовместимо с новой историей. Предпочтителен исправляющий
релиз вперёд. Возврат к старой версии требует отдельно проверенного восстановления
резервной копии с учётом записей, появившихся после неё; молча удалять их нельзя.

Задачи попадают в счёт после «Выполнено». Черновик прошлого месяца можно выставить
через историю; объединение нескольких расчётных месяцев в один счёт и авансы
этим изменением не добавляются. Визуальная приёмка в реальном Telegram остаётся
за владельцем; автоматические проверки не отправляют ему тестовые сообщения.
