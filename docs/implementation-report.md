# Отчёт о завершении реализации MVP

## Найдено и причины

Исходные 38 тестов SQLite проходили, но не проверяли диспетчер бота и рабочую
PostgreSQL-схему. В миграции отсутствовал `tasks.billing_period_id`; ORM теряла
timezone у нескольких дат. Не было обработчика карточки проекта, интерфейса
полей/заметок/регулярных услуг/напоминаний, ключа идемпотентности платежей и CI.
Ручные дозаказы использовали общий ключ `chat:None:msg:None`. Финансовые переходы
могли выполняться параллельно без блокировки строки.

## Исправлено

- Два новых шага Alembic; исходная опубликованная миграция не переписывалась.
- UTC-типы, DB-ограничения денег/валюты/месяца, защита финансовых ссылок от CASCADE.
- Единый порядок финансовых блокировок: клиент → задача/период; обновление состояния
  после захвата блокировки. Идемпотентные платежи, задачи и регулярные начисления.
- Полный путь от пересылки до оплаченного счёта; работа со скрытым отправителем;
  сохранение исходного сообщения при создании проекта и редактировании задачи.
- Карточки, поля, заметки, архив, услуги, поиск, история счетов и платежей, напоминания.
- Проверка владельца и личного чата, HTML-экранирование, отмена ввода, обработка ошибок.
- Исполняемая команда `crm-bot`, Docker с автоматическими миграциями, фиксация
  runtime-зависимостей, CI и документация запуска/резервного копирования.

## Проверено локально

- `ruff check app tests alembic` и `ruff format --check app tests alembic`.
- Полный прогон на PostgreSQL с `TEST_DATABASE_URL`, включая независимые
  конкурентные подключения, финансовые ограничения и диспетчер aiogram.
- Миграции `upgrade head → downgrade 0001_initial → upgrade head` на отдельной БД;
  `alembic check` не обнаруживает расхождений ORM и схемы.
- `docker build -t crm-for-me:local .` и реальный entrypoint контейнера:
  миграции выполняются, затем без Telegram-конфигурации возвращается ожидаемый отказ запуска.
- `docker compose --env-file .env.example config --no-env-resolution --quiet`.

## Smoke

Диспетчер + FSM + PostgreSQL, с подменой только транспорта Telegram:
пересылка → клиент → проект → задача 5000 → IN_PROGRESS → DONE → поле проекта →
услуга 5000 → повторная генерация без дублей → счёт 10000 → оплата 4000 →
долг 6000 → оплата 6000 → долг 0 → snapshot не меняется после изменения источника.

## Границы проверки и риски

Рабочего `.env` с токеном бота и ID владельца нет. Живой Telegram не подключался,
ручной проход в реальном чате не выполнен. Настройки и последовательность приёмки
описаны в README и `docs/acceptance.md`.

После выставления месячного счёта новые работы нельзя закрыть в этот же месяц;
корректировочные счета не входят в MVP. Напоминания при сбое между отправкой и
commit могут быть доставлены повторно. Незавершённый FSM-диалог после рестарта
сбрасывается; сохранённые данные остаются в БД.

Реализация блокировок сверялась с [SQLAlchemy AsyncSession](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html),
изоляция коротких диалогов — с [aiogram Dispatcher](https://docs.aiogram.dev/en/latest/dispatcher/dispatcher.html).
